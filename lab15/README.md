## Ответы на контрольные вопросы

### 1. Что такое система контроля версий и зачем она нужна?
Система контроля версий (VCS — Version Control System) — это программное обеспечение, регистрирующее изменения в одном или нескольких файлах на протяжении времени и позволяющее возвращаться к определенным предыдущим версиям, сравнивать изменения, отслеживать авторов правок и восстанавливать файлы в случае ошибок. VCS необходима для организации командной работы, предотвращения потерь кода, параллельной разработки нескольких функций (ветвление) и ведения прозрачной истории развития проекта.

### 2. Чем отличается Git от других систем контроля версий (SVN, Perforce)?
Главное отличие заключается в архитектуре: Git является распределенной системой (DVCS), тогда как SVN и Perforce — централизованными (CVCS).
* В Git каждый разработчик имеет локально полную копию репозитория со всей историей изменений. Это позволяет выполнять практически все операции (коммиты, ветвление, просмотр истории) локально, мгновенно и без постоянного сетевого подключения.
* Способ хранения данных: Git сохраняет данные как снимки (снапшоты) файловой системы во времени. Традиционные VCS (SVN) хранят информацию в виде списка изменений (дельта-разниц) файлов относительно базовых версий.
* Надежность: при падении центрального сервера в SVN работа блокируется, а потеря сервера грозит утратой истории. В Git любой локальный клон разработчика является полноценной резервной копией.

### 3. В каких трёх состояниях может находиться файл в Git?
В Git файлы проекта могут находиться в одном из трёх основных состояний:
1. **Modified (изменен)** — файл модифицирован в рабочей директории (Working Tree), но изменения еще не подготовлены для фиксации;
2. **Staged (подготовлен / проиндексирован)** — измененный файл добавлен командой `git add` в область подготовки (Staging Area / Index) и готов войти в следующий коммит;
3. **Committed (зафиксирован)** — изменения надежно сохранены в локальной базе данных репозитория Git (`.git/objects`) в результате выполнения команды `git commit`.

### 4. Какие основные команды Git вы знаете?
* `git init` — инициализация нового локального репозитория;
* `git clone <url>` — клонирование существующего удаленного репозитория;
* `git status` — проверка состояния рабочей директории и индекса;
* `git add <files>` — добавление файлов в область подготовки (индекс);
* `git commit -m "msg"` — фиксация проиндексированных изменений в репозитории;
* `git branch` / `git branch <name>` — просмотр существующих веток / создание новой ветки;
* `git checkout <branch>` / `git switch <branch>` — переключение на указанную ветку;
* `git checkout -b <name>` — создание новой ветки с одновременным переключением на нее;
* `git merge <branch>` — слияние указанной ветки в текущую (с флагом `--no-ff` создается merge-коммит);
* `git pull` — получение и слияние изменений из удаленного репозитория в текущую ветку;
* `git push -u origin <branch>` — отправка локальной ветки и коммитов в удаленный репозиторий;
* `git log --graph --oneline` — отображение истории коммитов в виде компактного графа.

### 5. Что такое ветка в Git и зачем она нужна?
Ветка в Git — это легковесный перемещаемый указатель на конкретный коммит в дереве репозитория (внутри `.git` ветка представляет собой файл размером всего 41 байт, содержащий 40-значный SHA-хеш коммита). При создании нового коммита указатель ветки автоматически сдвигается вперед.  
Ветки нужны для изоляции разрабатываемого функционала: разработчики могут параллельно выполнять различные задачи, не затрагивая стабильный код в ветке `master`/`main`, а по завершении — безопасно сливать код.

### 6. Что такое конфликт слияния и как его разрешить?
Конфликт слияния (merge conflict) возникает тогда, когда Git не может автоматически объединить ветки — как правило, если в обеих ветках были внесены разные изменения в одни и те же строки одного и того же файла, либо если файл в одной ветке был изменен, а в другой удален.  
Для разрешения конфликта:
1. Открывают конфликтующий файл, где Git расставил маркеры (`<<<<<<< HEAD`, `=======`, `>>>>>>> branch`);
2. Вручную или с помощью 3-панельного визуального редактора IDE (например, встроенного инструмента IntelliJ IDEA) выбирают результирующий вариант кода и удаляют разделительные маркеры;
3. Помечают файл как разрешенный командой `git add <файл>`;
4. Завершают процесс слияния командой `git commit`.

### 7. Что такое GitHub и чем он отличается от Git?
Git — это локальная консольная утилита контроля версий, работающая на компьютере пользователя и не требующая интернета.  
GitHub — это облачная веб-платформа и сервис хостинга Git-репозиториев. GitHub добавляет к функционалу Git развитые инструменты для совместной командной разработки: механизм Pull Request, код-ревью (Code Review), трекер задач (Issues), CI/CD автоматизацию (GitHub Actions), публикацию сайтов (GitHub Pages) и управление правами доступа.

### 8. Что такое Pull Request и зачем он нужен?
Pull Request (PR) — это механизм платформ совместной разработки (GitHub/GitLab), позволяющий разработчику предложить свои изменения из тематической ветки (или форка) для слияния в основную ветку репозитория.  
Pull Request необходим для:
* Проведения код-ревью: коллеги могут построчно просмотреть код, оставить комментарии и замечания до попадания изменений в основную ветку;
* Автоматической проверки (CI): запуска автоматических тестов и статических анализаторов;
* Обсуждения архитектурных решений и сохранения истории изменений и обсуждений.

### 9. Что такое файл .gitignore и зачем он нужен?
Файл `.gitignore` — это конфигурационный текстовый файл, расположенный в корне репозитория (или в его подпапках), содержащий шаблоны файлов и каталогов, которые Git должен игнорировать при индексации и фиксации.  
Он необходим, чтобы исключить попадание в репозиторий:
* Скомпилированных бинарных файлов (`.class`, `.jar`, папки `target/`, `out/`);
* Файлов настроек конкретной IDE (`.idea/`, `*.iml`, `.vscode/`);
* Служебных файлов операционной системы (`.DS_Store`, `Thumbs.db`);
* Файлов конфигураций с приватными паролями, токенами доступа и логов (`*.log`).
